# Журнал критики и редакций

## Clean-room пересмотр вердикта 1.1.30 и циклы 1.1.31–1.1.45

Новый аудит отменил прежний вывод о нулевом числе замечаний. Блокирующей причиной была неверная абстракция идентичности: текущий `lms load --exact` требует `ModelInfo.path`, а репозиторий передавал `modelKey`. Второе серьёзное замечание — порог LM Studio 0.4.1, предшествующий обновлённой chat template Gemma 4, добавленной в 0.4.11.

Версии 1.1.31–1.1.45 заменили поиск одного modelKey на уникальную локальную пару path/modelKey, добавили pre/postconditions и rollback по точному identifier, повысили минимум до 0.4.11 при рекомендации 0.4.20, синхронизировали двуязычные документы и каноническое имя репозитория, а также добавили регрессии, воспроизводящие оба исходных дефекта. Полный release gate и повторный прогон после чистой распаковки завершаются нулём критических замечаний.

## Цикл 6 — релиз 1.1.2

Буквальная имитация первой публикации показала, что `git add .` мог добавить неожиданный локальный файл, не попавший под `.gitignore`. Теперь публикуемый первый commit формируется только по инвентарю `SHA256SUMS`, а любой дополнительный untracked-файл останавливает процедуру. Примеры отчёта среды единообразно используют игнорируемый каталог `artifacts/`. ZIP применяет stored-записи и не зависит от реализации Deflate, а CI был переведён со старых major-тегов на выбранные в тот момент релизы v6 официальных GitHub Actions. Все четыре условия закреплены регрессионными тестами.

## Цикл 10

Критических замечаний при независимой проверке точности и отказных режимов: 4.

1. Поиск локальной модели мог принять другую квантизацию Gemma 4 26B A4B QAT, если Q4_0 отсутствовала; теперь требуются точные признаки QAT, GGUF и Q4_0, иначе сценарий завершается отказом.
2. Проверка манифеста не отклоняла каждый встроенный компонент `.` и не требовала уникального отсортированного состава; новый отдельный парсер проверяет весь манифест до сверки, staging, сравнения Git-инвентаря и упаковки.
3. Проверка loopback-сокета могла быть пропущена при отсутствии `lsof` и могла столкнуться с короткой задержкой запуска сервера; теперь `lsof` обязателен, а проверка выполняется с ограниченным числом повторов.
4. Команда `gh repo create --source . --remote origin` без необходимости связывала создание удалённого репозитория с изменением локального remote и могла конфликтовать с уже существующим `origin`; эти операции разделены.

Все четыре условия закреплены регрессионными тестами. После проверки готового артефакта и полной имитации публикации критических замечаний: 0.

## Цикл 10: аудит переопределения точного профиля

В версии 1.1.5 штатный поиск строго выбирал Q4_0, однако экспортированная переменная `MODEL_KEY` обходила этот поиск перед оценкой и загрузкой, а локальная конфигурация могла перенаправить скачивание на другой каталог или квантизацию и завершиться ошибкой лишь после сетевой операции. В версии 1.1.6 каждое переопределение проверяется по установленному инвентарю LM Studio, а изменение каталога или Q4_0 отклоняется до скачивания. Резервный разбор человекочитаемого вывода сначала использует `lms ls --variants`. Критических замечаний после повторной проверки: 0.

## Цикл 12

Критических замечаний при проверке идентичности публикации и границы tool-host: 2.

1. Документация обещала локальную Git-идентичность, однако автоматизация читала эффективные значения и поэтому принимала унаследованные глобальные `user.name` и `user.email`. Теперь оба значения обязательны именно в локальном `.git/config`, а функциональный тест доказывает отказ при наличии только глобальной идентичности.
2. Read-only пример инструмента принимал произвольный `--base-url` и ошибочно считал ложные JSON-значения `[]`, `null` или `false` эквивалентом пустого объекта аргументов. Теперь по умолчанию разрешён только числовой loopback-адрес, удалённый endpoint требует отдельного явного флага, принимается ровно один разрешённый вызов с непустым ID, а аргументы должны декодироваться строго в пустой JSON-объект.

После повторной проверки критических замечаний: 0.

Во время финальной имитации публикации обнаружено, что новый тест идентичности сам копировал `.git` из уже инициализированного исходного checkout. Теперь тест герметичен и исключает Git-метаданные, релизный вывод, локальные артефакты и Python-кэши до проверки отказа при одной лишь глобальной идентичности.

## Цикл 13

Критических замечаний при повторной проверке публикации и актуального LM Studio CLI: 4.

1. Неожиданный существующий `origin` молча переписывался на канонический SSH-адрес. Теперь публикация завершается отказом и требует, чтобы пользователь отдельно проверил любую исправляющую команду `git remote set-url`.
2. Поиск модели опирался на обычный JSON и человекочитаемый перечень вариантов, хотя современный `lms ls` предоставляет машинный инвентарь `--json --variants`. Теперь этот режим имеет приоритет, точный квантизованный ключ предпочитается базовому ключу модели, а устаревший `--detailed` больше не используется.
3. MCP-пример принимал `LM_NATIVE_BASE_URL` из окружения и мог передать тело запроса либо `LM_API_TOKEN` удалённому endpoint без отдельного подтверждения. По умолчанию разрешён только числовой loopback; удалённая отправка требует `--allow-remote-base-url` и сопровождается предупреждением.
4. Запуск сервера выводил `lms server status`, но игнорировал его ошибки. Теперь машинный статус обязан подтвердить `running=true` на настроенном порту до независимой проверки loopback-сокета.

Для существующего GitHub-репозитория также проверяются архивное состояние и точное совпадение visibility; они не меняются неявно. После детерминированной упаковки и полной имитации публикации критических замечаний: 0.

Аудит состояния публикации выявил противоречивый контракт: helper предлагал private-режим, тогда как Release, badges README и заданный профиль требуют публичный репозиторий. В 1.1.18 автоматизация поддерживает только Public и после создания и редактирования проверяет owner/name, visibility, archived state, description и default branch. Критических замечаний после повторной проверки: 0.

## Независимый цикл для версии 1.1.19

Критических замечаний: 1. Шаблон benchmark был намеренно оставлен в состоянии «не измерено», но это состояние и полнота полей не контролировались машинно; ручная правка могла создать видимость канонического результата с вымышленными или внутренне противоречивыми числами. Версия 1.1.19 добавляет fail-closed валидатор доказательств, связывает результат с точной версией репозитория, аппаратным и модельным профилем и вводит assurance case, сопоставляющий утверждения, механизмы, тесты и остаточную аппаратную неопределённость. После исправления критических замечаний: 0.

## Завершающий независимый цикл для версии 1.1.20

Критических замечаний: 1. Цель `make test` была псевдонимом полного конвейера проверки, а не семантически прямой точкой запуска регрессионных тестов; кроме того, отсутствовала отдельная fail-closed проверка устаревшей текущей версии сразу во всех эксплуатационных документах. Версия 1.1.20 напрямую запускает изолированный runner через `make test`, добавляет `make version-check`, включает контроль версий в `verify_repo.sh` и функционально доказывает отказ при устаревшей ссылке. После исправления критических замечаний: 0.

### Дополнительная завершающая перепроверка внутри 1.1.20

Критических замечаний: 2. Локальная конфигурация могла уменьшить пороги памяти, диска и macOS либо задать `REQUIRE_API_AUTH=0`, что противоречило объявленному защищённому профилю. Кроме того, reader версии удалял все пробельные символы до проверки и принимал ошибочное содержимое вида `1.1. 20`. Финальная 1.1.20 вводит общий неослабляемый gate для preflight, скачивания, оценки, загрузки, сервера и проверки аутентификации, делает аутентификацию безусловной и проверяет буквальное содержимое VERSION без нормализации пробелов. Функциональные тесты доказывают отказные режимы. После исправления критических замечаний: 0.

### Перепроверка rollback запуска внутри 1.1.20

Критических замечаний: 1. Если после `lms server start` не проходила проверка listener или аутентификации, сценарий завершался, но мог оставить новый сервер работающим; особенно опасен был отказ именно проверки аутентификации. Финальный сценарий запрещает захватывать уже работающий сервер и устанавливает rollback trap, который при последующей ошибке останавливает только сервер, запущенный этим сценарием. Функциональный mock-тест доказывает вызов остановки. После исправления критических замечаний: 0.

### Перепроверка постусловий метаданных GitHub внутри 1.1.20

Серьёзных замечаний: 1. Публикация проверяла identity, visibility, archived state, описание и ветку по умолчанию, но доверяла коду возврата `gh repo edit --add-topic`, не доказывая наличие всех канонических topics. Финальное постусловие читает `repositoryTopics` и машинно проверяет обязательное множество. После исправления серьёзных замечаний: 0.
